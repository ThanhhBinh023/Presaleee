## Defects and behaviour findings recorded by this run

| # | Area | Finding |
| --- | --- | --- |
| F1 | G13-02 / code | Pipeline stage counts were produced by a single `GROUP BY l.status, p.currency` query and then overwritten row by row, so a stage holding proposals in more than one currency reported the count of one currency group instead of its lead count (QUALIFIED showed 1 instead of 3). Fixed by counting leads per status in its own query and keeping the currency sums for the value list. |
| F2 | G13-04 / code | `parseLimit()` treated an empty query value as 0 and answered 400, while every other list endpoint reads `?limit=` as "not provided", and its message named the parameter `limit` even for `leadLimit`. Fixed: empty means default, and the message names the parameter. |
| F3 | G13-08 | `GET /dashboard/activity` is synthesized from `leads.created_at/updated_at` and `proposals.created_at/updated_at`, not from `audit_logs`: the feed equals that SQL row set exactly, while the audit table holds several times more events for the same tenant. Each entity can contribute at most two rows (one `:created`, one `:updated`), so a later edit overwrites the previous one and intermediate events are unrecoverable. Actions that never move an entity timestamp — sheet writes, pricing apply, portal sessions, deletes — never appear. The test plan expected this feed to reconcile with G14; it cannot. |
| F4 | G13-05 | The dashboard list endpoints answer `meta.total = data.length`, not the tenant-wide count, so a widget cannot know that more rows sit behind `limit`. Every other list in the API returns a real total. |
| F5 | G14-04 | `AUDIT_RESULT_STATUSES` defines `SUCCESS` and `FAILED`, and no code path writes `FAILED`: a rejected login and a rejected write leave no trace, so any security view filtered on FAILED is permanently empty. |
| F6 | G14-09 | Proposal create, metadata edit, sheet write and delete are not audited (only status transitions and pricing apply are), and meeting/discovery, knowledge and RAG usage write nothing at all. The ledger cannot answer "who wrote this section". |
| F7 | G13-11 / code | `dashboardRoutes.ts` applies `requireAuth` + `requireOrganization` only, so a VIEWER reads the full revenue pipeline. Read-only, but the same guard gap already recorded for the knowledge vault and the portal reads. |
| F8 | G14-05 | `from`/`to` are validated as ISO-8601 individually but never compared: `from=2099&to=2020` is a silent empty result rather than a 400. |
